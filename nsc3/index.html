NSC3

Designing new capabilities as part of a coherent product.

UX designerJanuary 2026–present

ContextProblemProcessSolutionPrototypingImpact

Context

NSC3 is a real-time situational-awareness and secure-communications platform for control-room operators and mobile field personnel. It brings video, location information and communications into a shared operational picture, including in degraded network environments.

I work across the critical-communications portfolio, but primarily as NSC3’s sole designer. My role is broad. Needs come from sales, support staff working with customers, and product management. I work with the product manager and developers to turn those that line up with the roadmap into clear requirements and fit them into the existing product, while keeping it coherent and usable for existing customers.

Problem

A customer request is the starting point. The design has to work across the product.

Control-room operators needed to know when their sources captured something that required their attention. An AI detection or a body camera being activated, for example. NSC3 needed to improve as a situational-awareness platform. I defined these occurrences as an “Events” concept. Then I needed to work out how to fit them into the product.

The challenge was to define one understandable workflow across these sources, while preserving Tasks as the place where teams coordinate their response.

Process

For Events, I designed a dedicated log with inspection on the same page. I organised the information around the operator’s questions: what happened, where, when, how it was detected, what has been done about it and what can be done next.

Operators inspect an Event before deciding whether to create a Task or send an Alert. Personal notification criteria let them decide in advance which Events should demand their attention.

I considered adding Task creation directly to Event inspection. I kept the existing dialog because saving one click didn’t justify changing a pattern operators already used elsewhere in the product.

Solution

From a detection to a deliberate response.

Inspect and coordinate a response

Keep the event log visible during inspection. The first design stacked the inspection area above the log. Later iterations placed the selected Event in an adjacent panel, keeping the surrounding Events visible while the operator examines the evidence and available actions.

  1. Inspect alongside the event log. Review a selected Event without losing its context.
  2. Organise evidence. Group the detection, supporting media and relevant details for assessment.
  3. Continue into action. Start a Task or Alert from Event inspection.
  4. Coordinate the response. Continue the response through the Task and Alert workflows.

When an Event calls for a response, the operator can create a Task or send an Alert from the inspection panel. Tasks provide a place to coordinate the work. Alerts reach selected recipients and track their acknowledgements. I refined the requirements and designed the Web and Mobile experiences for this Targeted Alerting workflow, including delivery through SMS and LiveLink.

Manage competing demands for attention

The interface evolved as field reports exposed another problem: too many Events competing for attention. I reframed the next phase around personal subscriptions, notifications and better inspection. Subscriptions let Controllers define which Events should notify them; filtering narrows the log they are reviewing. In the inspection image above, the notification bells show which Events match subscriptions, and the “Notified events” filter helps operators focus on those matches. These capabilities were deployed to a later face-recognition POC.

Resolving a design debate: subscription placement

Design reviews often involve debating several possible solutions. With Event subscriptions, I thought the controls belonged on the Events page: they were closely related to the Events, and users would find them in context. The product director thought users would look under Manage, based on his experience and analysis of competing products.

We couldn’t test the alternatives with users at that point. I prepared designs for both options and brought their pros and cons to a team review. We discussed them and went with the product director’s preference.

The discussion was useful because it brought discoverability into focus. As I developed the Manage design, I paid particular attention to how the subscriptions were placed and labelled so users could find them and recognise them as their own.

Design and review behaviour in code

I came across an article by Alpha Design Partners about AI-native design maturity and used its framework to structure an initiative for improving how we design and build with AI. I broke the work into milestones covering the design system, guidance for coding agents and prototyping in code.

I adapted the existing design system by aligning Figma variables with code tokens and adding guidance for coding agents to the product repository. This gives agents shared rules and components for NSC3 Web development, including prototypes. I also established a prototyping environment within the development codebase, so I could design and review interactions using the product’s actual components.

I define the requirements in Jira epics and tickets, design the interface in Figma, then direct AI to build an interactive version in the prototyping environment I’ve built into our development environment. There I can work through the states, flows and interactions. Prototypes use fictional data and simulated services.

The workflow in practice: Event image viewer. I used Figma to establish the layout and a coded prototype to refine zooming, panning and behaviour at narrower window sizes. I completed the design and prototype on the same day, then reviewed the interaction with our Web developer.

Our Web developer used the image-viewer prototype code as a starting point for implementation, describing it as mostly usable as is.

Impact

From ambiguous requests to implemented POC workflows.

Developers implemented the Events concept, and it was deployed to partner POCs. Subscriptions, notifications and filtering followed in the later face-recognition POC, while Targeted Alerting was deployed for its own customer exercise.

Alongside these product capabilities, I established a code-based workflow for design reviews and implementation handoff. The scrum team has used it to review new interactions, and the image-viewer prototype supplied a developer with code to start implementation.
